# tic-tac-toe v1 — design

**Status:** Draft for review
**Date:** 2026-07-22
**Depends on:** x0x ADR-0023 (durable local history), x0x REST/WS API (142+ endpoints), x0x-symphony (agent orchestration, v2)

## 1. Product thesis

The agent-workspace category is now validated (Block's Buzz, July 2026).
Every entrant in that category shares one architectural weakness: a relay or
server in the middle, and pre-quantum signatures end-to-end. x0x removes
both. tic-tac-toe is the smallest product that makes that difference
*visible to a user in the first five minutes*:

> Install on two machines. No sign-up, no server, no configuration. You have
> a shared workspace with history, search, private groups, and agents — and
> a network tap between the two machines shows nothing but PQC-signed QUIC.

Everything in v1 either serves that five-minute experience or is cut.

## 2. What v1 is

A desktop app (macOS first, Linux/Windows follow) with:

| Surface | Backing x0x capability |
|---|---|
| Onboarding (name → identity) | Machine/Agent keys auto-generated by `x0xd`; optional User key stays opt-in |
| Contacts + presence | `/contacts`, trust levels, presence events (SSE/WS) |
| Direct messages | `/direct/send` + WS, **history + search via ADR-0023** |
| Channels (public groups) | Named groups `public_open` preset |
| Private groups | Named groups `private_secure` (TreeKEM/MLS) |
| History & search everywhere | `GET /history`, `GET /history/search`, WS backfill-then-live |
| Agent roster | Agents appear as contacts/members exactly like humans; agent cards (`/agent/card`) render role + capabilities |
| File drop | Existing 1 GB chunked file transfer |

### Explicit v1 non-goals

- Agent *orchestration* UI (attach/configure harnesses) — v2, via symphony + ACP.
- Company templates — v2 (see §6).
- Media galleries / content store — after x0x content-store design lands.
- Cross-node history backfill — gated on its own future x0x ADR.
- Nostr compatibility — that is the bridge's job, not this app's.
- Git hosting (Buzz has it; not our proof point).

## 3. Architecture

```
┌────────────────────────────────────────────┐
│ tic-tac-toe (desktop shell)                │
│  UI state, rendering, notifications only   │
└──────────────┬─────────────────────────────┘
               │ REST + WS (loopback, token auth)
┌──────────────▼─────────────────────────────┐
│ x0xd (spawned or attached, --name ttt)     │
│  identity · gossip · groups · MLS ·        │
│  presence · files · history (ADR-0023)     │
└──────────────┬─────────────────────────────┘
               │ QUIC + PQC (ant-quic)
               ▼  the mesh
```

Rules that keep this honest:

1. **The app holds no protocol state.** If tic-tac-toe is killed and
   restarted, everything rehydrates from `x0xd` (history store + live WS).
   The app's only persistence is window geometry and UI preferences.
2. **Daemon-only integration.** tic-tac-toe uses the same REST/WS surface as
   any third-party app — no private crate APIs. This dogfoods the public
   surface and keeps the app portable to any x0xd version that passes the
   API parity suite.
3. **Spawn-or-attach.** On launch: discover a running `x0xd` (token
   auto-discovery), else spawn `x0xd --name ttt` with a bundled binary.
   Self-update stays the daemon's job.

### Stack decision (revised 2026-07-22)

## 4. The history dependency (why ADR-0023 ships first)

Chat UIs are, mechanically, history viewers with a live tail. Without
ADR-0023 every scroll-back, every search, every restart is a special case.
With it, the core UI loop is one protocol shape:

```
WS subscribe {scope, backfill: true}
  → stored events (oldest → newest)
  → {type: "live"}
  → live events
```

v1 therefore sequences **behind** the history store landing in x0xd, and
tic-tac-toe's acceptance suite doubles as ADR-0023's product validation
(history-after-restart and search are acceptance tests #1 and #2).

## 5. Proof-point acceptance suite

Scriptable, CI-able, demo-able:

1. **Cold two-node workspace:** fresh daemons on two machines (or two
   `--name` instances), no config → DM round-trip < 10 s from first launch.
2. **History survives:** send 50 messages, `kill -9` both daemons, restart →
   full scroll-back + FTS hit on message #17.
3. **PQC end-to-end:** packet capture during (1) shows QUIC only;
   `/history` rows carry ML-DSA-65 signatures that re-verify offline.
4. **Private group:** 3-member TreeKEM group; ban one member; banned member's
   next message rejected; survivors' history intact across epoch advance.
5. **Agent member:** a headless agent (x0x crate or daemon) joins a channel,
   answers a message, appears in roster with its agent card — same identity
   machinery as the humans.
6. **Zero listeners:** `lsof` on both machines shows no listening TCP socket
   except the loopback API — nothing a third party could connect to.

## 6. v2 direction — agents, skills, and company templates

The deep-dive concept: **agent/skill pairs** composed into org charts, e.g.
Marketing = social-watcher (agent+skill) + copywriter (agent+skill), with
named groups as departments, KV as shared memory, task lists as work queues,
symphony as the orchestrator, SKILL.md as the skill format.

A **company template** is a declarative bundle:

```toml
[template]            # e.g. "software-dev-and-sales"
groups = [...]        # departments (presets, policies)
[[agent]]             # role, skill refs, harness (ACP: goose/codex/claude)
[[workflow]]          # symphony WORKFLOW.md refs
[[store]]             # KV/task-list scaffolding
```

Instantiation is symphony's job; tic-tac-toe's v2 UI renders and manages it.
First template: **software dev + sales** — dogfooded on Saorsa itself before
any other vertical (consultancy, legal, accounting, medical, veterinary…)
is authored. Verticals are data, not code; none are built until the bundle
format survives dogfooding.

Borrow from Buzz at this layer: the **Agent Client Protocol** for
harness-agnostic agent attachment, so Goose/Codex/Claude-Code agents slot
into templates without bespoke adapters.

## 7. Risks

| Risk | Mitigation |
|---|---|
| ADR-0023 slips → app has no substrate | History store is scoped small (lift the bridge's tested store); build UI against a stub daemon fixture in parallel |
| Convergence latency variance (44 ms best-case, seconds under cold mesh — measured 2026-07-22) | UX designs for eventual delivery: optimistic send, delivery states from DM ACKs; never a spinner on the mesh |
| Two-frontend split (communitas vs tic-tac-toe) | Different categories (collaboration canvas vs agent workspace); revisit merge only after v1 ships |
| Buzz ships faster than we do | We are not racing Buzz feature-for-feature; the proof point is the four claims in README §Proof point, which Buzz cannot make |

## 8. Milestones

Milestones map onto the staged fork plan (`buzz-fork-plan.md`):

- **M0 — substrate:** ADR-0023 store lands in x0xd (endpoints + CLI +
  restart-survival test green). Parallel: fork Stage 0 (hygiene, Playwright
  mock suite green in our repo).
- **M1a — "Buzz UX, x0x mesh" messaging core (fork Stage 1):** embedded
  x0xd + bridge v2 (WS dialect, AUTH, `/events`, extended `/query` +
  search, `thread_metadata`, `/info`); unmodified Buzz UI, mock +
  relay-mode messaging/thread/search Playwright suites green, zero relay
  servers. Acceptance tests 1 and 6 pass — this is the five-minute demo.
- **M1b — media + invites (huddle: ship-or-cut decision):** Blossom
  surface + invite/join-policy API; remaining relay-mode suites green.
- **M2 — identity flip (Stage 2):** x0x AgentId is the displayed identity;
  npub gone from UI. Acceptance test 3 passes end-to-end.
- **M3 — native data layer (Stage 3):** per-feature migration to x0xd
  REST/WS + history backfill; bridge removed from the app. Acceptance
  tests 2, 4, 5 pass; full Studio functional pass.
- **M4 (v2 opens) — symphony/ACP + first company template (Stage 4).**
